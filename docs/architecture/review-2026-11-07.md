# Architecture Review: Confirmed Findings

Reviewed: 2026-11-07. Frontend baseline `54740b1`; backend `0cbfd15`.
Scope: active frontend/backend paths and reporting lifecycle, with the local MCP
checkout inspected for contract parity. Production state was not inspected.

This report builds on the [current system map](README.md). It identifies concrete
architectural mistakes through their behavioral consequences, not through folder
names or preferences for a particular framework.

Priorities: P1 = silent reporting error or loss of an available successful result;
P2 = reliability/contract/release issue needing correction in normal development.
These are engineering priorities, not security incident classifications.

## Findings

### A1. P1: Contact-Owned Data Has Competing Read Authorities

Evidence:

- Backend `analytics_dashboards/attribution.py:42` reads tags from
  `Opportunity.contact_snapshot` and `relations`, not `Contact.tags`.
- `analytics_dashboards/lead_cohort.py:156` and `booking_activity.py` use that
  attribution resolver.
- `analytics_dashboards/calculations.py:270` reads current `Contact.tags` for
  In Sequence.
- `crm/services.py:50` and `:374` update normalized contacts and opportunity
  embedded contact copies through different sync paths.

Confirmed scenario: a normalized contact has tag `google-new` while its opportunity
copy still has `meta-old`; source attribution chooses Meta. Refreshing contacts
alone cannot reconcile that source. Different metrics can interpret the same
contact using different copies of contact-owned state.

The architectural error is not retaining source snapshots. It is the absence of
an explicit authoritative input policy at the reporting boundary. The current
opportunity copy is neither guaranteed current contact state nor a deliberately
immutable acquisition-time attribution record.

Lean direction: normalize a reporting input projection once, batch-load current
contact evidence when that is the intended semantics, and make any snapshot
fallback explicit with provenance. If acquisition-time attribution is required,
persist that separately instead of treating a mutable embedded copy as history.

Regression coverage: conflicting contact/opportunity tags, contact-only refresh,
missing normalized contact, multiple opportunities and explicit source priority.

### A2. P1: Calculation Fingerprint Does Not Describe Its Actual Dependencies

Evidence:

- Backend `analytics_dashboards/configuration.py:98` and `:104` freeze/hash
  dashboard JSON, excluding display and period-selection settings.
- `analytics_dashboards/calculations.py:136` loads live `SourceFieldMapping`
  records for Expected Value; `lead_cohort.py` loads a live Dentrix mapping.
- `analytics_dashboards/refresh_service.py:95` freezes dashboard JSON, not the
  effective semantic mappings used later by the calculator.
- Dashboard GET checks version/hash to select a current result.

Confirmed scenario: changing the expected-value mapping from one contact custom
field to another changed the calculated value from 1,000 to 2,000 with an identical
dashboard calculation-config hash. Thus a result can remain labeled current
after a calculation rule changes. A queued run is only partially frozen.

The inverse problem also exists: changing only a metric's presentation tone in
the JSON changes the hash and invalidates results even though no formula changed.

Lean direction: define an effective calculation specification that includes
semantic mapping IDs/revisions or normalized mapping values, rule configuration,
period/timezone policy and calculation version. Persist it with the run/result.
Keep labels, colors, icons and display composition outside its data-validity hash.
This does not require versioning all source data or adding a formula language.

Regression coverage: mapping edit invalidation, queued-run mapping freeze, and
presentation-only changes preserving calculation validity.

### A3. P1: Calendar Comparison Uses Rolling-Duration Arithmetic

Evidence: backend `analytics_dashboards/contracts.py:25`, `DateRange.prior`,
subtracts the current period's number of days regardless of period semantics.
Calculators use this range for prior comparisons.

Confirmed scenario: canonical `month:2026-10` compares against
`2026-08-31..2026-09-30`, not the previous calendar month
`2026-09-01..2026-09-30`. Monthly comparisons include the wrong records even
though the selector displays discrete calendar months.

The abstraction is too generic: a date interval and a reporting-period policy
are not interchangeable. Matching durations is useful for rolling windows, not
the universal definition of a prior month.

Lean direction: centralize prior-period resolution by period kind. Calendar
month uses prior month bounds; week uses prior week; partial/rolling intervals
need an explicit comparison policy. Let frontend labels consume that policy.

Regression coverage: 28/29/30/31-day months, year boundaries, partial month policy
and workspace timezone boundaries.

### A4. P1: Growth Review Overwrites Result State With Attempt State

Evidence: backend `growth_reviews/reactivation_dashboard_service.py:42` uses
`update_or_create` on the existing campaign/result/version row and sets it running
before building a replacement payload. On failure it sets the same row failed.
`get_completed_reactivation_campaign_result` only reads completed rows.

Confirmed scenario: a successful stored payload remains physically in the row
after a failed recalculation, but its status is failed and no completed fallback
is selectable. A temporary calculation failure makes the previous good result
unavailable to the normal read path.

The core problem is conflating a calculation attempt with the last successful
materialized result, not simply that Growth Review has a different table name
from Analytics.

Lean direction: keep attempt/run state separate. Calculate into a new result or
replace the current payload only after success; retain the last successful result
while exposing failure/progress alongside it. Full migration to Analytics is not
needed to fix this lifecycle.

Regression coverage: failure/retry with an existing result, reads during running,
successful replacement and concurrent refresh exclusion.

### A5. P1: Frontend Reconstructs Business Conversion From Independent Counts

Evidence:

- Backend `growth_reviews/funnels/reactivation_calculator.py:52` independently
  matches each reached-step signal for cohort records.
- Frontend `widgets/dental-growth-review/reactivationCampaignKpiModel.js:57`
  divides all booked contacts by all replied contacts and labels it
  `Reply -> Booking`, with text saying those bookings are from the replies.

Confirmed synthetic input: 36 cohort, 3 replies, 10 booked produces `333%` and
`10 of 3 replies booked`. The input contract does not guarantee booked is a subset
of replied; independent stage totals cannot establish a conversion intersection.

Lean direction: calculate the actual replied-and-booked population in the owning
backend calculator and return numerator, denominator, value and temporal/date
basis. Frontend should format these semantics, not infer them from stage names.
Do not cap the percentage at 100%; that would conceal the population error.

Regression coverage: booked without a reply, replied without booking, overlap,
zero denominators and renamed display labels.

### A6. P2: Refresh Identity Is Replaced By A Coarse Dashboard Lock

Evidence:

- Backend `analytics_dashboards/refresh_service.py:85` returns any active run for
  the dashboard before comparing requested period or config identity.
- The API returns 202 with that run, not an explicit different-target conflict.
- Frontend `features/analytics-dashboard-data/useAnalyticsDashboardReadModel.js:45`
  attaches the returned run to the requested context without validating its period.
- Before POST returns, the hook stores `refresh: null`; `isRefreshing` depends on
  a known active run rather than an explicit submitting state.

Confirmed scenario: enqueue Oct 19-25, then request Oct 26-Nov 1; the second call
returns the Oct 19 run and does not create the requested report job. Current UI
disables many actions once it knows an active run, but another tab/API consumer
or the pending-request window can still encounter this behavior.

Serializing work per dashboard is a reasonable resource policy. Silently treating
different commands as the same command is not idempotency.

Lean direction: distinguish request identity (dashboard + canonical period +
effective config) from execution lock scope. Reuse an identical active request;
return an explicit conflict for a different one, or queue it intentionally.
Expose created/reused/conflict plus actual target. Model frontend state as
submitting/queued/running/terminal and validate the returned target.

Regression coverage: double-click pending response, identical request across tabs,
different period/config while active, reload and network failure.

### A7. P2: Catalog And Read Path Do Not Share Result Selection Policy

Evidence: backend `analytics_dashboards/period_catalog.py:16` retains completed
older-version snapshots as stale, while `analytics_dashboards/views.py:237`
filters both normal and stale fallback selection to the current calculation
version. Frontend receives contradictory statements about the same report.

Confirmed scenario: the catalog exposes a completed stale report with snapshot
ID; GET for that period responds `not_calculated` with no snapshot.

Lean direction: one backend selection service should define current/stale/
unavailable and payload readability. Both catalog and dashboard GET consume it.
If a payload version cannot be rendered, distinguish unsupported-version from
never-calculated rather than silently discarding its existence.

Contract drift is broader: backend/normalizer allow `heatmap` while the renderer
has no implementation; MCP 0.6.1 settings/period schemas lag current frontend.
These additional cases are source-confirmed, not separately browser-tested.

Regression coverage: API catalog -> select each returned report -> consistent
read state; renderer coverage for every advertised widget; MCP adapter parity.

### A8. P2: Production Has Multiple Incompatible Build/Release Paths

Evidence:

- `.github/workflows/static.yml:27` runs plain `npm run build` on `main`.
- Manual deployment uses `npm run build:github-pages`.
- `vite.config.js:34` and `:45` inject production API/hash routing defaults for
  `github-pages`, not ordinary production mode.
- `shared/api/backendApiClient.js:10` throws on a remote host without API config.
- Current frontend source branch is `dev`; workflows track other branch sets.

Configuration evaluation confirmed ordinary production mode has no injected API
or routing mode, while github-pages mode has the remote API and hash routing.
The CI workflow does not supply the missing values. A clean CI run can therefore
publish a different/nonworking runtime contract from manual deployment.

Lean direction: one explicit build command/configuration per deploy target,
consumed by both CI and manual deployment. Align intentional release branches and
add an artifact check for required API/routing/site settings. Do not infer that
source push means both web and worker processes were updated.

This is a checked-in pipeline finding, not a claim that today's live site is
currently serving that CI artifact.

### A9. P2: Queued Is A Persistent State Without Worker-Liveness Semantics

Evidence:

- Backend `/health/` in `client_portal/urls.py:23` returns a constant ok response.
- `background_jobs/worker.py:44` executes full domain jobs sequentially.
- `analytics_dashboards/refresh_service.py:279` expires stale running leases,
  not queued jobs; recovery itself requires a running processor.
- Frontend polls while a run remains queued/running, without distinguishing an
  unavailable worker from ordinary waiting.

Consequences: if the worker stops, HTTP can be healthy and requests accepted
while UI remains Updating indefinitely. A long Growth job also delays the next
Analytics job in the single sequential sweep. These are source-level failure
scenarios; no live worker was stopped in this audit.

Lean direction: retain the management-command worker if its throughput is
sufficient, but record worker heartbeat/queue age and expose truthful waiting/
unavailable/stalled states. Establish bounded operational recovery and supervisor
restart procedures. Separate sync freshness from report calculation so calculating
several historical periods need not blindly repeat full source sync each time.
Do not add a distributed queue solely to repair missing liveness reporting.

## Structural Debt: Important, But Not Equal To The P1 Findings

### Competing Runtime Architectures Remain In The Frontend

`AuthProvider.jsx:9` disables local repository operations, while large retained
domain services and old architecture guidance still assume that runtime.
Some active service barrels import old service modules, so even entry-point
reachability is not proof that all exported operations are usable.

This creates an onboarding/AI-maintenance trap: a new feature can follow a
documented service pattern that cannot run in the active application.

Lean direction: mark/isolate the retired runtime and its retained features;
identify active public APIs; reconcile the main architecture guide with current
runtime. Do not mass-delete all unreachable files without product decisions.

### Module Boundaries Are Mostly Conventions

Examples: Integrations calls CRM upserts while CRM imports Integration mapping
models; Workspace tag catalog imports Growth Review signals; worker package
imports domains while they import its retry helpers. Frontend API calls live in
domain services, entity APIs and workflow hooks. ESLint does not enforce imports.

Direct ORM reads and a modular monolith are not themselves mistakes. The risk is
the lack of explicit ownership/interfaces where a change crosses several domains.

Lean direction: define public entry points for source normalization, effective
report inputs, result selection and job commands. Move genuinely generic retry
utilities below domain orchestration if that reduces coupling. Add focused
boundary checks, not repository interfaces around every Django model.

### Large Files And Tests Do Not Align With All Cross-Layer Invariants

Hotspots include Growth Review blocks/workflow, GHL synchronization, workspace
views and Analytics calculations. Size indicates candidates for responsibility
splits, not proof of poor implementation by itself.

The inspected test organization covers layers locally but does not establish
the catalog/read, mapping/invalidation, frontend conversion population and
cross-period command invariants above. No current maintained Playwright setup
was found in frontend package/config. Green unit/build checks cannot certify
these end-to-end contracts.

Lean direction: add regression/contract tests for each confirmed issue before
extracting its policy or service. Split large files along those ownership lines,
not an arbitrary maximum line count.

## What Is Not An Architectural Error By Itself

- Django modular monolith rather than microservices.
- Django services using ORM without a repository layer.
- Different Growth Review and Lead Report visual card variants.
- Keeping specialized Growth Review beside the newer Analytics platform during
  an incremental migration.
- Backend-owned calculation and permission checks.
- Frontend generating missing calendar periods from backend calendar policy.
- Retaining a simple sequential worker while its limits are explicit and supported.

## Suggested Repair Order

1. Restore reporting truth: A1/A2/A3/A5 with regression tests.
2. Protect available results and command semantics: A4/A6/A7.
3. Make delivery/execution observable and deterministic: A8/A9.
4. Isolate retired frontend runtime and clarify public module APIs.
5. Extract shared reporting infrastructure only where a stable repeated policy
   has been demonstrated; migrate Growth Review later without erasing its domain.

The next step should be scoped repairs, not a complete rewrite, a generic
dashboard builder, an event-sourcing platform or a universal metric component.

## Verification Performed

Seven temporary Django diagnostic tests were run against a fresh in-memory test
database, destroyed afterward. They asserted the current undesired behavior:

1. Old completed snapshot in catalog versus not-calculated dashboard GET.
2. Different-period enqueue returns existing period's run.
3. Failed Growth recalculation removes normal completed-result availability.
4. Tone-only presentation edit changes calculation hash.
5. October's prior comparison includes August 31.
6. Source attribution uses stale opportunity tag copy rather than current contact.
7. Expected-value mapping changes the value without changing dashboard config hash.

All seven reproduced their target conditions. A separate pure Node probe
reproduced the 333% Reply-to-Booking output. Vite configuration was evaluated for
ordinary production versus github-pages modes.

The diagnostic tests were ephemeral, not added to the repository's permanent
regression suite. Existing full suites, browser scenarios, load/concurrency tests
and production/security audits were not run. No application code, customer data,
production configuration or deployed processes were changed.
